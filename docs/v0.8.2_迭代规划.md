# v0.8.2 迭代规划 — 回测诊断、AI归因与交易语义重构

> 版本：v0.8.2 | 创建：2026-05-09
> 基于：v0.8.1 当前主线

---

# 一、升级目标

v0.8.1 已具备：

- 七层分析链路（Signal → Decision → Event → AI → Strategy → Execution）
- 纯历史回测模式（AI/事件禁用）
- 严格框架回测 `framework_strict`
- 兼容模式回测 `legacy_compatible`

但在 9 只股票、多个时间区间（近一年/半年/一季度）的人工回测中，暴露出新的核心问题：

- ❌ 大部分样本明显跑输买入持有
- ❌ 交易频率过高，减仓过于频繁
- ❌ 系统没有清晰的“买点 / 卖点”语义
- ❌ 清仓后再入场能力弱，容易长期空仓
- ❌ 极端行情触发后直接清仓，防守过猛
- ❌ 当前回测结果文本不适合直接交给 AI 做深度归因

v0.8.2 的本质：

从“能跑回测” → “能解释为什么跑输 / 为什么频繁交易 / 为什么拿不住”

从“连续加减仓系统” → “具备明确交易语义的中线持有系统”

从“规则拼盘持续叠加” → “可解释、可验证、可维护的量化研究框架”

# 二、当前问题总结

## 2.1 回测结果层面的直接信号

从 `tests` 目录中的 9 个回测结果文本看，已经能得出几个稳定结论：

1. 多数样本在近一年、近半年、近一季度都跑输买入持有。
2. 交易次数显著偏高，季度级别可达到 16~18 次，一年可达到 50+ 次。
3. 胜率和盈亏比普遍偏弱，说明交易不仅多，而且质量一般。
4. 趋势强、走势流畅的股票也经常跑输买入持有，说明系统“拿不住赢家”。

这意味着问题不只是“某些参数不合适”，而更可能是：

- 信号结构偏日线化，缺少中长期过滤器
- 策略层对偏弱信号过度响应
- 卖出语义没有分层，导致涨了减、跌了也减
- 止盈 / 止损 / 趋势结束 / 战术减仓被压成了同一类动作

## 2.2 当前回测模式暴露出的具体行为问题

### 问题 1：清仓以后再无动作

当前表现：

- 清仓后往往进入长时间空仓
- 后续即使股价重新走强，也难以重新进入

可能原因：

1. `CLOSE_ALL` 后进入 `COOLDOWN`，抑制再入场
2. 再入场条件要求过高，单次 `BUY` 信号难以重新触发建仓
3. `WATCH/HOLD` 与 `OPEN` 的映射不够清晰，导致“看多但不动手”

### 问题 2：极端行情下直接清仓

当前表现：

- 遇到极端波动时，系统倾向于快速 `CLOSE_ALL`
- 这对于短线风控是合理的，但对于中线持有系统过于激进

问题本质：

- 当前极端行情更多体现为“风险立即出清”
- 没有区分“中线趋势破坏”与“短期剧烈波动”

### 问题 3：缺少明确买点和卖点概念

当前系统更像：

- 偏多就 `OPEN/ADD`
- 偏弱就 `REDUCE/CLOSE_ALL`

但缺少以下明确语义：

1. 首次入场买点（Entry）
2. 趋势确认加仓点（Add）
3. 正常持有（Hold）
4. 战术减仓点（Trim）
5. 趋势结束卖点（Exit）
6. 风险止损卖点（Stop）

结果就是：

- 买点不够明确
- 卖点过于泛化
- 动作频繁而缺少中长期一致性

# 三、主流量化框架对照与方向校验

## 3.1 对照对象

本轮方向评估参考以下主流框架与研究平台：

- QuantConnect / LEAN
- Backtrader
- Freqtrade
- Qlib
- Zipline

这些项目的侧重点不同，但行业共识高度一致：

1. 信号、组合/仓位、风控、执行必须解耦。
2. 回测评估不能只看收益，还要看换手、成本、偏差、样本外稳定性。
3. 诊断能力和研究流程，通常比继续增加指标更重要。
4. 入场与出场语义必须清晰，否则系统容易变成高频碎调仓。

## 3.2 对照表

| 框架 | 核心设计 | 行业理念 | 对本项目的启示 |
|------|----------|----------|----------------|
| QuantConnect / LEAN | Alpha → Portfolio Construction → Risk → Execution | 强调职责分离、模块可替换、研究驱动开发 | 当前七层架构方向总体正确，但必须收紧层边界，避免 Strategy Layer 变成第二个 Alpha |
| Backtrader | Strategy + Order + Broker + Analyzer | 重视事件驱动、订单语义、成交现实约束 | 交易动作与订单语义要更清楚，回测分析器应成为正式模块 |
| Freqtrade | Indicator → Entry / Exit → Trade Management | 明确 entry / exit 语义，强调查偏和 forward test | 当前最该补的是 entry / exit 语义拆分，以及 lookahead / 回测偏差检查 |
| Qlib | Forecast → Decision Generator → Executor → Analyser | 研究、决策、执行、分析是完整工作流 | 当前新增 AI 分析导出和分层诊断是正确方向，后续要补正式 Analyzer 与实验记录 |
| Zipline | 事件驱动回放 + Pandas 研究生态 | 简洁研究接口、统计分析、性能输出 | 保持研究链条简洁，不要把系统复杂度主要加在规则堆叠上 |

## 3.3 结论：当前方向哪些是对的

与主流框架对照后，可以确认以下方向是正确的：

1. 先做分层诊断，而不是继续盲调参数。
2. 先重构交易语义，而不是继续叠加信号。
3. 先补 AI 可分析导出与归因能力，而不是继续看终端摘要。
4. 先解决“拿不住赢家 / 卖得太碎 / 清仓后回不去”的结构问题。

## 3.4 结论：当前方向哪些需要收紧

与主流框架对照后，也能明确以下风险点：

1. 不能继续新增大层级，应优先收紧现有层级边界。
2. AI 当前只能优先做信息理解、解释增强、回测归因，不能过早深入主交易触发。
3. Decision 与 Strategy 的职责必须更清晰，避免 Strategy Layer 同时承担信号生成、行为约束、仓位控制、风控判定四种职责。
4. 评价体系必须升级到行业常用指标，而不只是收益、回撤、夏普。

# 四、为什么需要“Decision only / + Strategy / + Execution”分层回测

## 4.1 这三个版本分别在看什么

### A. Decision only

只跑：

`Signal → Decision`

不跑：

- Strategy Layer
- Execution Layer

作用：

- 只看“原始信号判断”有没有方向优势
- 不关心冷却、确认、惯性、滑点、涨跌停等问题

如果这个版本就跑输买入持有，说明：

- 基础信号结构本身有问题
- 文章逻辑映射到代码后已经偏了

### B. Decision + Strategy

只跑：

`Signal → Decision → Strategy`

不跑：

- Execution Layer

作用：

- 看策略层行为约束有没有把原始信号“压坏”
- 检查过度保守、过度冷却、过度确认、过度减仓

如果 `Decision only` 还行，但 `+ Strategy` 明显变差，说明：

- 当前策略层机制过强或语义设计不合理

### C. Decision + Strategy + Execution

即当前严格框架：

`Signal → Decision → Strategy → Execution`

这就是当前 `framework_strict` 在纯历史回测中的真实交易结果。

作用：

- 看现实成交成本和执行限制会吃掉多少优势

如果 `+ Strategy` 尚可，但 `+ Execution` 明显变差，说明：

- 执行层约束或交易频率导致的成本过高

## 4.2 当前你的测试属于哪一层

你现在 `tests` 目录下的 9 只股票结果，全部属于：

- `framework_strict`
- 也就是 `Decision + Strategy + Execution`

所以现在的结论只能说明：

- 最终成品策略表现不好

但还不能说明：

1. 是原始信号错了
2. 还是策略层太保守 / 太频繁
3. 还是执行层成本和限制把收益吃掉了

这也是 v0.8.2 需要新增分层回测模式的原因。

# 五、AI回测分析输入设计

## 5.1 当前 `.txt` 结果为什么不够

当前 `tests` 中的文本结果主要包含：

- 汇总收益指标
- 交易次数
- 稳定性指标
- 部分执行约束统计

但对于 AI 归因分析仍然不够，因为缺少：

1. 全量交易记录（完整原因、动作语义、持仓比例变化）
2. 每日账户快照（资产曲线、回撤形成过程）
3. 每日决策追溯（DecisionTrace）
4. 被策略层压制的动作统计
5. 清仓后再无动作的上下文原因
6. 极端行情触发前后的状态变化

因此 v0.8.2 应新增可直接交给 AI 的结构化导出，而不是仅靠终端文本。

## 5.2 建议给 AI 的完整输入结构

建议每次回测新增一个 `backtest_analysis_payload.json`，至少包含以下字段：

## 5.3 AI分析时必须附带的三张表

### 表 1：分层回测表

用途：判断问题出在信号、策略层还是执行层。

字段建议：

| 字段 | 说明 |
|------|------|
| stock_code | 股票代码 |
| period | 近一年/半年/一季度 |
| layer_mode | decision_only / decision_strategy / decision_strategy_execution |

用途：回答“为什么会买 / 为什么会减 / 为什么会清仓”。

字段建议：

| 字段 | 说明 |
|------|------|
| date | 日期 |
| final_signal | 最终信号 |
| position_action | 动作 OPEN/ADD/REDUCE/CLOSE_ALL |
| trigger_type | entry / add / trim / exit / stop |

| position_ratio_after | 动作后仓位 |

### 表 3：持仓破坏表

用途：回答“本来可以继续拿，为什么被系统打断”。

字段建议：

| 字段 | 说明 |

| date | 日期 |
| stock_code | 股票代码 |
| hold_context | 当日原本持有背景 |
| broken_by | 是什么打断了持有 |
| broken_reason | 具体原因 |
| from_state | 原状态 |
| to_state | 新状态 |
| pnl_if_hold_5d | 如果继续持有5天的收益 |
| pnl_if_hold_10d | 如果继续持有10天的收益 |

# 六、给 AI 的分析逻辑（Prompt 思考框架）

## 6.1 AI不是直接评价输赢，而是做“归因”

AI分析要求：

1. 先判断回测输赢是否主要来自交易频率、拿不住赢家、过度止盈、极端清仓、无法再入场等结构问题。
2. 再判断问题属于：
   - 信号层
   - 策略层
   - 执行层
3. 最后给出结构性改进建议，而不是只说“优化参数”。

## 6.2 标准 AI 分析 Prompt 模板

```text
你是一个负责回测归因分析的量化诊断助手。

下面会给你一份完整的回测分析数据，包含：
1. 汇总指标
2. 全量交易记录
3. 每日账户快照
4. 分层回测表
5. 动作来源表
6. 持仓破坏表

你的任务不是简单评价收益高低，而是回答以下问题：

一、表现归因
1. 跑输买入持有的主要原因是什么？
2. 问题主要来自信号层、策略层还是执行层？
3. 是“不会买”还是“拿不住”还是“卖得太碎”？

二、交易结构诊断
1. 买点是否明确？
2. 卖点是否明确？
3. 是否存在“涨了减、跌了也减”的模式？
4. 清仓后再无动作是否普遍存在？
5. 极端行情清仓是否过度？

三、持仓行为诊断
1. 哪些交易本应继续持有却被过早打断？
2. 哪些减仓属于合理止盈，哪些属于过度保守？
3. 赢家是否被系统过早卖出？

四、输出要求
请按以下结构输出：
1. 核心结论（3-5条）
2. 分层归因（信号层/策略层/执行层）
3. 典型坏案例（列举3笔）
4. 最值得优先修改的3个机制
5. 不建议轻易改动的机制
```

## 6.3 AI分析输出要求

AI输出必须能回答：

1. 系统到底输在何处
2. 哪个机制最值得先改
3. 哪类股票最不适合当前版本
4. 哪些卖出动作属于“拿不住”
5. 哪些约束会导致清仓后再无动作

# 七、v0.8.2 开发原则与重构方向

## 7.1 五条持久化开发原则

以下五条作为 v0.8.2 起的长期开发原则，需同步用于代码、文档、回测、评审：

### 原则 1：不再新增大层级，优先收紧边界

当前七层架构已足够表达系统职责。

后续重点不是继续加层，而是：

- 明确 Decision 只负责方向判断与信号表达
- 明确 Strategy 只负责行为约束与交易语义映射
- 明确 Execution 只负责成交现实约束

### 原则 2：先诊断，再调参

参数不是第一优先级。

如果没有分层归因，盲目调参只会让系统越来越复杂。

### 原则 3：先重构交易语义，再重构参数

当前系统最大的问题不是某个阈值，而是交易语义不清晰。

### 原则 4：AI 先做研究增强与解释增强，不直接扩权到主交易触发

AI 当前适合承担：

- 新闻与事件理解
- 回测归因分析
- 研究辅助与文档辅助

AI 当前不适合承担：

- 直接输出主交易触发
- 在未完成分层验证前主导买卖动作

### 原则 5：优先修复“拿不住赢家”，并以中线持有目标约束设计

如果趋势强股也大幅跑输买入持有，说明系统不是不会识别机会，而是不会持有机会。

## 7.2 行业校准后的重构方向

### 方向 A：交易语义重构

当前动作过于依赖：

- `OPEN`
- `ADD`
- `REDUCE`
- `CLOSE_ALL`

建议在语义层显式拆成：

| 语义 | 说明 |
|------|------|
| ENTRY | 明确入场买点 |
| ADD | 趋势确认后加仓 |
| HOLD | 正常持有，不操作 |
| TRIM | 战术减仓，不代表趋势结束 |
| EXIT | 趋势结束退出 |
| STOP | 风险止损退出 |

这样可以避免：

- 所有 `SELL` 都变成减仓 / 清仓
- 所有偏多都变成建仓 / 加仓

### 方向 B：买点重构为“结构化触发”，而不是连续打分自然溢出

当前问题：买点偏连续打分，缺少结构化触发。

建议：

1. 首次建仓必须要求明确 `ENTRY` 信号
2. 加仓必须要求趋势确认，而非简单“仍偏多”
3. 月线 / 周线作为方向和位置过滤器，日线只负责触发点

### 方向 C：卖点重构为职责分明的退出体系

当前问题：卖点过于泛化，导致频繁减仓。

建议：

1. 止损卖点和趋势结束卖点彻底分开
2. 止盈只允许 `TRIM`，不能轻易 `EXIT`
3. 极端行情先区分“短期剧烈波动”还是“趋势破坏”
4. 建仓后设置最短持有窗口，避免刚进就减

### 方向 D：多时间框架回归主导地位

策略库核心思想之一：

`月线定方向 → 周线定位置 → 日线找买卖点`

当前问题：

- 代码仍以日线为主
- 上位周期缺少硬过滤地位

v0.8.2 建议：

1. 月线方向不过，不允许日线 `ENTRY`
2. 周线位置不佳，不允许日线 `ADD`
3. 日线只负责执行层面的精确触发

### 方向 E：验证体系前置到重构之前

在主流框架中，研究流程和偏差检查通常先于大规模调参。

v0.8.2 需正式纳入：

1. 分层回测对照
2. 样本内 / 样本外验证
3. 交易频率、持有天数、成本后超额收益评估
4. lookahead bias 与数据口径偏差检查

# 八、实施计划

## Phase 1：回测诊断导出层（最高优先级，已完成）

### 目标

让每次回测结果可直接交给 AI 分析，而不是依赖手工阅读终端文本。

### 调整说明

本阶段不要求先改动回测引擎核心统计口径，优先通过 Reporter 层和 CLI 导出能力建立分析输入。

# 九、验收标准

v0.8.2 不以“收益立刻变高”为唯一目标，而以“能明确诊断原因”为第一验收标准。

第一阶段验收标准：

1. 每次回测都能导出完整 AI 分析 payload
2. AI 能基于 payload 输出一致、可操作的归因结论
3. 能清楚回答：
   - 为什么跑输买入持有
   - 为什么交易频繁
   - 为什么拿不住赢家
   - 为什么清仓后再无动作

当前判断：已基本达成，后续重点转向跨层结果合并与模板化分析。

第二阶段验收标准：

1. `Decision only / +Strategy / +Execution` 三层都可跑
2. 能识别问题主要出在信号、策略还是执行

当前判断：第 1 条已达成，第 2 条已具备单次导出的层级归因基础，但仍缺少自动化多层对照输出。
当前判断：第 1 条已达成，第 2 条已基本达成；后续重点转向 merged timeline 与更正式的 comparison analyzer。

第三阶段验收标准：

1. 已具备基础偏差检查能力
2. 能明确区分“策略错”与“回测口径失真”
3. 至少具备一套样本外验证流程

第四阶段验收标准：

1. 趋势强股的持有能力明显改善
2. 年度和季度交易次数显著下降
3. `REDUCE` 次数下降，`EXIT` 语义更明确

# 十、结论

当前系统的核心问题，不是“策略文章没价值”，而是：

1. 文章中的中长期思维尚未被完整映射到代码结构里
2. 买卖点语义不清晰
3. 策略层对偏弱信号过度响应
4. 回测缺乏分层归因和 AI 可读导出
5. 研究流程和偏差验证还未正式制度化

v0.8.2 的第一任务不是继续盲调参数，而是建立：

- 分层诊断能力
- AI 可分析能力
- 清晰的交易语义
- 研究验证纪律

只有这样，后续参数优化和结构重构才是有方向的。

与主流量化框架对照后的最终判断是：

- 当前优化大方向正确
- 但必须严格限制“继续加层 / 继续加信号 / 继续放大 AI 权限”这三类冲动
- v0.8.2 应以“边界收紧、语义清晰、验证前置”为核心执行原则
