# RAG 评估体系：现状盘点 vs 业界标准（含建议）

- 日期：2026-09-11
- 触发问题：「rag_eval 只有一个测试，是否太少了点？这个测试足够评估 RAG 的能力吗？」
- 结论口径：**不够。它测的那一层（检索）是必须的地基，但只覆盖了 RAG 能力的约 1/3；缺的是生成层、端到端层，以及最关键的"人工金标"和"负样本"。**
- 本报告只做现状 + 对照 + 建议，**不新增任何测试**（遵你第 3 条：先评估、后决定）。

---

## 一、先纠正一个计数：`rag_eval` 不是"一个测试"

| 你可能以为 | 实际 |
|---|---|
| 1 个测试函数 | `evaluator.py`（301 行）是一个**检索质量评估工具**，内含 30 条查询的批量评估 + 报告输出，**不是** pytest 用例 |
| 它在回归里跑 | **不在**。跑法是手工 `python tests/rag_eval/evaluator.py`，且 `pytest` 全量命令显式 `--ignore=tests/rag_eval` |
| RAG 只有这一处测试 | 另有 `tests/rag/` **5 个文件 35 个用例**（分块/多样性/系列隔离/重排/索引新鲜度）——但那些是**功能回归**（"代码有没有按预期工作"），不是**质量评估**（"检索得准不准"）。两者不是一回事，不能互相替代 |

**所以真实情况是：功能回归有 35 条，质量评估只有 1 个工具、30 条查询、且只测检索。** 这个组合的短板在"质量"那一侧。

---

## 二、现状：这个评估工具到底测了什么（全部实测）

### 2.1 它在做什么

```
30 条测试查询（15 个类别）
   ↓  RAGService.retrieve(top_k=5)
   ↓  与前一步用同一 embedder 算的相似度自动打标（cosine ≥0.72 = relevant，≥0.60 = partial）
   ↓  Recall@5 / MRR / NDCG@5 + 分类别汇总
   ↓  与目标值比对 PASS/FAIL，写 eval_report.json
```

### 2.2 当前基线（`eval_report.json` 实测）

| 指标 | 当前值 | 目标 | 判定 |
|---|---|---|---|
| Recall@5 | **0.633** | 0.70 | ❌ **未达标** |
| MRR | 0.553 | 0.50 | ✅ |
| NDCG@5 | 0.568 | 0.50 | ✅ |
| 查询数 | 30 | — | 偏少（业界单元级 5-10、开发级 50-100、生产基线 200-300） |
| avg_ndcg@5 | 0.568 | — | — |

**5 条查询 Recall@5 = 0.0**（q09/q10/q15/q17/q18，集中在"技术指标/技术/操作"类）——即**完全没检索到任何相关文档**，这是最该看的一批 bad case，但当前工具只打印、不做任何闭环。

> ⚠️ 数字漂移提醒：`.workbuddy/memory` 里记的是「Recall@5 = 0.800」（v0.8.0 时代）。当时知识库远小于现在的 837 块，且 2026-09-05 修过标注口径（P1-B：查询侧改用带 BGE 前缀的 `embed_query`，此前用 `embed()` = 用无前缀分布判相关性 = **循环验证、分数虚高**）。**两个数字不可直接比较**，别拿 0.800 当"退化了"的结论。

### 2.3 结构性短板（这才是"够不够"的答案）

1. **只测检索层，生成层完全空白**：AI 拿着检索结果有没有胡说、有没有答非所问、有没有用上上下文——一个都没测。而 RAG 的典型失效恰恰"看着很像对"（有引用、语气自信、但内容不被检索结果支撑）。
2. **标注与检索同源（自证循环）**：标签是用**同一个 embedder 的相似度**自动生成的。P1-B 修掉了"查询侧无前缀"这个具体错误，但**同源**这一层没变——用 A 打分再拿 A 评估 A，指标天然偏高。业界共识是**先有人工金标，再上 LLM 判定**（"不要一开始就用 LLM-as-judge，未校准的裁判会给你自信的垃圾"）。
3. **没有负样本**：30 条全是"知识库里应该有答案"的问题。业界建议 ~20% 是**已知不可答**的问题（考系统会不会老实说"不知道"）。本项目这类问题的失效后果尤其重——投资建议场景编造答案的代价远高于普通问答。
4. **不在任何回归路径上**：改分块策略 / 换嵌入模型 / 动重排开关 / 改 top_k 之后，**没有东西会提醒你去跑它**。业界做法是把它做成 CI 门禁（"recall@5 掉超过 2% 就阻断合并"）。
5. **查询量偏少且类别不均衡**：15 个类别里 8 个只有 1-2 条（"资金"1 条、"规则"1 条），单条查询的波动直接决定该类别分数 → 类别级结论不可靠。

## 三、业界标准：测什么、怎么测、阈值多少

### 3.1 三层评测架构（最主流的骨架）

```
端到端层   答案正确性 · 有用性 · 拒答校准 · 格式合规
   ↑ 生成层   忠实度 Faithfulness · 答案相关性 Answer Relevancy · 上下文利用率 · 引用质量
   ↑ 检索层   上下文精确率 · 上下文召回率 · MRR · Hit Rate@K · nDCG
```

核心洞察（多份资料一致）：**最终质量是乘法不是加法**——检索或生成任一层拉胯，整体归零。**只测端到端 = 知道坏了但不知道哪里坏**；只测检索层 = 知道找得准不准、不知道答案有没有胡说。

### 3.2 检索层：经典 IR 指标（本项目已有 3/5）

| 指标 | 测什么 | 什么时候用 |
|---|---|---|
| Recall@K | 相关文档里，Top-K 捞到了几成 | **首选**（A 股知识库场景：漏掉证据 = 答案没戏） |
| Precision@K | Top-K 里有几成是相关的 | 控噪（Top-K 开太大时） |
| MRR | 第一个相关文档排在第几位 | 只要一个最佳来源时 |
| nDCG@K | 分级相关性 + 位置折损 | 排序质量（本项目已有） |
| Hit@K | Top-K 里有没有至少一个相关的 | 粗基线 |

### 3.3 生成层：RAGAS 四指标（2026 事实标准）

| 指标 | 人话 | 需要金标答案吗 | 生产阈值 |
|---|---|---|---|
| **Faithfulness** | 答案里每句话，都能在检索到的内容里找到依据吗（= 有没有胡编） | 否（LLM 判定） | ≥0.75（优秀 ≥0.85~0.90） |
| **Answer Relevancy** | 答案真的回答了这个问题吗（= 有没有答非所问） | 否 | ≥0.80 |
| **Context Precision** | 检索回来的内容里，有多少是真正有用的 | 否 | ≥0.70 |
| **Context Recall** | 回答所需的信息，是否都被检索到了 | **是** | ≥0.75 |

**诊断矩阵**（比单个分数有用得多）：

| 指标组合 | 病根 | 修复方向 |
|---|---|---|
| 高 Faithfulness + 低 Answer Relevancy | 检索跑偏（照搬了错材料） | 换嵌入/查询改写 |
| 高 Context Recall + 低 Faithfulness | 材料对了但模型乱编 | 强化提示词/降温度/换模型 |
| Precision 与 Recall 双低 | 基建坏了（分块/索引） | 先修底层，别怪 LLM |
| 四项全高 | 健康 | 持续监控 |

口诀：**答案跑偏查检索，内容乱编查生成，全线拉胯查基建。**

### 3.4 方法论要点（容易踩的坑）

| 要点 | 说明 |
|---|---|
| **先人工金标，再上 LLM 判定** | 未校准的匿名裁判 = 自信的错误答案。人工标注 50-200 条起步 |
| **裁判模型 ≠ 生成模型** | 同族同模型会自我偏好。本项目有 DeepSeek + Kimi 两家 → 可交叉当裁判 |
| LLM-as-judge 四大偏置 | 位置偏置（随机化）、长度偏置（长度归一）、自我偏好（换模型族）、风格偏置（按 rubric 打分） |
| 裁判校准 | 抽 10% 让 (人) 复核，一致率 <80% 视为裁判漂移，需重新校准 |
| 评测集规模 | 单元 5-10 / 开发 50-100 / 生产基线 200-300；**<50 条不要下结论** |
| 覆盖配比 | ~60% 常见问题、~20% 边界（多跳/对比）、**~20% 已知不可答** |
| 成本量级 | LLM 判定的评估约 **$0.001-0.003 / 用例**（本项目 30 条 × 四指标 ≈ 几分钱一次） |
| 别用 BLEU/ROUGE | 它们测表面文字重合度，对 RAG 几乎无用（措辞不同也可能都对，流畅的胡编也能得高分） |

### 3.5 落地流程（业界通用的 7 步）

1. 建金标集（50-200 条真实查询 + 正确来源文档；来源=用户日志/工单/手写）
2. 定相关性判据（二元用于 Recall；0-3 分级用于 nDCG）
3. 跑基线（当前 pipeline 的 recall@5 / MRR / nDCG@5）→ 这是后面对照的基准
4. 单变量迭代（一次只动分块/嵌入/混合权重/重排）→ 重跑 → 只保留有提升的
5. 进 CI（每次动检索相关代码就重跑，掉超过阈值就阻断）
6. 线上抽样监控（本项目无线上流量，可跳过）
7. 失败案例回流金标集（每条用户报错的答案变成一个新用例）

## 四、差距对照

| 业界要素 | 本项目现状 | 差距等级 |
|---|---|---|
| 检索层 IR 指标 | ✅ Recall@5 / MRR / NDCG@5 | 已有 |
| 检索层 Precision@K / Hit@K | ❌ 无 | 小缺口 |
| 上下文精确率/召回率（Context Precision/Recall） | ❌ 无 | **中缺口** |
| 生成层 Faithfulness | ❌ 无 | **大缺口（最该补）** |
| 生成层 Answer Relevancy | ❌ 无 | **中缺口** |
| 端到端答案正确性 | ❌ 无（且需要金标答案 + 人工，成本最高） | 大缺口（暂不建议） |
| 人工金标 | ❌ 无（自动同源标注） | **大缺口（是上面所有 LLM 判定的前置条件）** |
| 负样本（不可答） | ❌ 无 | **大缺口（投资场景后果最重）** |
| 查询集规模 | 30 条（业界开发级 50-100） | 中缺口 |
| CI 门禁 | ❌ 不在任何回归路径 | 中缺口 |
| 裁判模型去同源 | 不适用（尚无 LLM 判定） | — |
| 线上监控 | 不适用（无线上流量） | — |

## 五、建议（分档，供你挑；我不擅自开工）

### 档 0：零成本，今天就能做（强烈建议）
- 把 `tests/rag_eval/evaluator.py` 写进 **"RAG 相关改动后必跑清单"**（改分块/嵌入/重排/top_k/知识库）
- 把当前基线数字（Recall@5 0.633 / MRR 0.553 / NDCG@5 0.568）写进 `AGENTS.md`，作为对照基准
- 人工过一遍 5 条 Recall@5=0.0 的 bad case → 大概率能直接定位是分块问题还是词典问题（**性价比最高的一步**）

### 档 1：小成本（推荐，约半天工作量）
- **补负样本**：加 6-8 条"知识库里没有答案"的查询（如问非本知识库领域），考系统是否会硬答
- **人工复核现有 30 条标注**：把同源自动标注改成人工确认（30 条 ×5 = 150 个判定，可控），消除自证循环
- 补 `Hit@K` 与 `Precision@5`（纯计算，几行代码）
- 收益：检索层从"自评"变成"可信"，这是后续所有 LLM 判定的地基

### 档 2：中等成本（可选，需你拍板）
- 引入生成层评估：用 **Kimi 当裁判评 DeepSeek 生成的答案**（或反之），算 Faithfulness + Answer Relevancy
- 需要先有"金标答案"或至少"金标来源文档" ⇒ 依赖档 1
- 成本极低（30 条 × 四指标 ≈ 几分钱一次），但**引入新依赖**（RAGAS 或自研 60-80 行判定器）
- 我更倾向**自研轻量判定器**而不是引入 RAGAS：项目已有 OpenAI 兼容客户端、已有 `evaluator.py` 的报告骨架，自研能复用且不引入 langchain 生态

### 档 3：不建议现在做
- 端到端答案正确性（需要人工金标答案，成本最高、收益滞后）
- 线上监控 / 漂移检测（本项目没有线上流量，做了是空转）
- 把评测集扩到 200-300 条（先把 30 条做扎实比堆量更有价值）

## 六、我的结论（一句话）

**"1 个工具 30 条查询"对一个知识库只有 837 块、且已跑通在线检索的系统来说——作为"有没有退步"的报警器够用，作为"RAG 能力行不行"的体检报告远远不够。** 缺的不是指标数量，而是三样东西：**人工金标（可信度）、负样本（敢不敢说不知道）、生成层（会不会胡说）**。建议按 **档 0 → 档 1** 走，档 2 等你评估后再定。

> 附：本报告所有"业界"论断均来自 2026-09 的公开资料（RAGAS 官方实践、生产 RAG 评估指南、检索评估指南等），数字（阈值/规模/成本）为多来源交叉后的常见取值，非单一出处；项目侧数字全部来自本仓库实测文件。
