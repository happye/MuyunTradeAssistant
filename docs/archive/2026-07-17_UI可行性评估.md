## 1. 核心结论：架构已具备 UI 基础，可行性高

**最大发现**：项目已经有一个"绕过 CLI、直调底层引擎"的解耦层--`src/chat/tools.py` 的 `TOOL_REGISTRY`。它的设计原则（tools.py:1-7）明确写着：

> - 绕过 CLI 层（CLI 层用 Rich Console 打印，无返回值）
> - 直接调底层引擎（Orchestrator/ScannerEngine/PortfolioManager/NewsClient/RAGService）
> - 返回数据

所以"UI 要加数据接口层"这个核心障碍**已经部分解决**。UI 不用从零搭接口，复用这个模式即可。

---

## 2. 架构三层现状（✅ 实证）

| 层 | 位置 | 职责 | 返回 |
|---|---|---|---|
| **底层引擎** | `Orchestrator` / `ScannerEngine` / `PortfolioManager` / `NewsClient` / `backtest_engine` / `benzong.auto_score` | 业务逻辑 | **结构化数据**（StockData / decision_result / candidates / positions / 回测结果对象）|
| **Chat 工具层** | `chat/tools.py` + `chat/formatter.py` | 调引擎 + format 转字符串 | **str**（给 AI 读）|
| **CLI 层** | `cli/main.py`（analyze_live / scan_market / run_backtest 等）| 调引擎 + console.print | **无**（print-only，业务逻辑混在 print 里）|

关键事实：
- `tools.py:151` `_orchestrator.analyze(...)` 返回 `decision_result, strategy_decision, execution_eval, ai_result`（结构化）
- `tools.py:191` `_scanner_engine.quick_scan(...)` 返回 `candidates, scan_info`（结构化）
- `tools.py:162` `format_analysis_result(...)` 把结构化数据**压扁成字符串**给 AI

**底层引擎已解耦返回数据，是 CLI 层和 formatter 把数据 print/字符串化了。** UI 要做的就是：调引擎（复用 tools.py 调用模式），拿结构化数据，自己渲染。不碰 CLI print 层。

## 3. UI 改造路径（复用，不重构）

- **不动 CLI 层**（analyze_live 等 print-only 不改，REPL 可保留作 fallback）
- **不动底层引擎**（已返回数据）
- **UI 新增一层**：调底层引擎（复用 tools.py 的调用模式）+ 自己渲染面板
- **可选优化**：重构 `tools.py` 把"调引擎拿数据"和"format 转字符串"分离，UI 复用前者、chat 复用后者。这步可选（UI 也可直接调引擎，不强制重构 tools.py）

改造量：**中等偏小**。不重构核心，新增渲染层。

## 5. 推荐：textual TUI

理由（对准你的情况）：

1. **解决"单线滚动"根因**：TUI 多面板布局--scan 结果表常驻左侧，选中股深度分析显示右侧，不用上下滚动。这正是你要的"优雅"。
2. **rich 已装是 textual 底层**：渲染风格和现有 CLI 一致（颜色/表格/面板），不突兀，学习曲线平滑（rich 你已间接在用）。
3. **Python 原生，你可维护**：不像 web 要懂前后端 + 部署。textual 是纯 Python，你改起来门槛低。
4. **终端用户契合**：你现在就是终端用（双击 start.py 进 REPL），TUI 还是终端，不切换场景。
5. **和现有架构集成成本低**：调底层引擎（tools.py 模式），不碰 CLI。

**streamlit web 的劣势**（对你）：交互模型是"脚本重跑"，复杂多步工作流（scan→选股→深度→加仓→回测串联）受限；web 你没经验，前端+部署维护门槛高；切换场景（终端→浏览器）。
