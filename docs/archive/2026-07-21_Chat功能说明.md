> 撰写日期：2026-07-21
> 适用版本：v0.8.1（Phase 5 引入，v0.8.1 增加 RAG 知识检索）
> 目的：让未来迭代时能在 5 分钟内看懂 chat 功能的全貌、关键文件、数据流与已知局限。

---

## 一、它是什么

Chat 是一个**自然语言对话入口**：用户用一句中文提问，AI（DeepSeek/Kimi）作为"调度大脑"，自主决定调用哪些底层分析引擎，再把多份结构化结果综合成一段人话回答。

定位上它**不是新引擎，而是现有引擎之上的一个 AI 编排层**：
- 复用 CLI 已有的 `Orchestrator / ScannerEngine / PortfolioManager / NewsClient / RAGService`
- 绕过 CLI 层（CLI 层用 Rich Console 直接打印，无返回值），直接调底层引擎拿数据
- 输出统一为纯文本（AI 要读纯文本，Chat 终端也用 `print()`）

核心机制是 **OpenAI Function Calling**：AI 返回 `tool_calls` → 执行工具 → 结果回传 → AI 再生成回复，循环最多 3 轮。

## 三、文件结构

```
src/chat/
├── __init__.py     # 导出 ChatAgent, run_chat_repl
```

## 四、核心架构（三层）

```
┌─────────────────────────────────────────────────────────┐
│  ChatAgent (agent.py)                                    │
│  - OpenAI 客户端（独立于 AIModifier，复用 settings.yaml） │
│  - 对话历史 _messages（system + 滑动窗口 N 条）           │
│  - function calling 循环（max_tool_rounds=3）            │
└──────────────┬──────────────────────────────────────────┘
               │ tool_calls（JSON）
               ▼
┌─────────────────────────────────────────────────────────┐
│  tools.py  TOOL_REGISTRY                                 │
│  search_stocks_by_sector / analyze_stock / scan_market   │
│  get_portfolio / get_news / search_knowledge             │
└──────────────┬──────────────────────────────────────────┘
               │ 纯文本结果（formatter 格式化）
               ▼
┌─────────────────────────────────────────────────────────┐
│  底层引擎（与 CLI 共用）                                   │
│  Orchestrator(7层分析) ScannerEngine(初筛)               │
│  PortfolioManager(持仓) NewsClient(新闻) RAGService(知识)│
└─────────────────────────────────────────────────────────┘
```

**关键设计约束**（见 [agent.py:1-13](../src/chat/agent.py:1)）：
1. 独立 OpenAI 客户端，不复用 `AIModifier` 实例
2. 纯文本输出，不用 Rich Console
3. 对话历史用滑动窗口控制 token

## 五、对话流程（function calling 循环）

以"分析茅台"为例，[agent.py:132 _run_conversation](../src/chat/agent.py:132)：

```
用户: "茅台怎么样"
  │
  ▼
[第 1 轮] 把 messages 发给 AI（含 tools 定义 + tool_choice=auto）
  │
  ├─ AI 返回 tool_calls: analyze_stock(stock_code="600519")
  │
  ├─ 执行工具：_execute_tool("analyze_stock", {stock_code:"600519"})
  │    └─ tools.py → Orchestrator.analyze() → formatter.format_analysis_result()
  │    └─ 结果超 4000 字符则保留首尾各 1950、截中间（M5 修复，见下）
  │
  └─ 工具结果作为 role=tool 消息追加进 messages
  │
  ▼
[第 2 轮] 再把 messages 发给 AI
  │
  └─ AI 无 tool_calls → 返回纯文本（最终人话回答）→ 结束
```

- 循环上限 `max_tool_rounds=3`，超过则强制再发一次**不带 tools** 的请求拿最终回复（[agent.py:202-215](../src/chat/agent.py:202)）。
- `temperature=0.3`，但对 `kimi-k2.5/k2.6` 不传（这些模型不支持，[agent.py:95-103](../src/chat/agent.py:95)）。
- `timeout=180`（M-H1 修复：原 60s 与 max_tokens=384K 矛盾致长回复超时白等，改 180s + 显式 `max_retries=2`）。
- 历史裁剪：保留 system + 最近 `max_history_messages=20` 条（[agent.py:120-124](../src/chat/agent.py:120)）。

## 七、配置项（configs/settings.yaml）

```yaml
chat:
  enabled: true
  max_history_messages: 20    # 对话历史最大条数
  max_tool_rounds: 3          # 单次对话最大工具调用轮次
  max_result_length: 4000     # 工具结果最大字符数（防 token 爆炸）

ai:
  provider: "deepseek"        # 或 kimi
  deepseek:
    base_url: "https://api.deepseek.com"
    model: "deepseek-v4-flash"   # deepseek-chat 2026-07-24弃用->v4-flash；V4默认思考模式，非思考需调用处传thinking.type=disabled
    api_key: ""               # 实际 key 放 configs/settings.local.yaml 或环境变量
```

## 八、两类"截断"——务必区分

迭代时最容易混淆的点：chat 里有**两个不同的截断**，分别在不同环节、不同原因。

### 8.1 工具结果截断（已修复，正常工作）
- 位置：[agent.py:236-238 _execute_tool](../src/chat/agent.py:236)
- 阈值：`max_result_length=4000`
- 策略：超长时**保留首尾各 1950 字符、截断中间**（M5 修复）
- 原因：`format_analysis_result` 把"决策理由/风险提示"放末尾，旧代码 `result[:max-100]` 只留头部，会把末尾的理由切掉，导致 AI 基于残缺信息回答。

### 8.2 AI 回复截断（2026-07-21 已修复）
- 位置：[agent.py](../src/chat/agent.py) `_call_api()` + 两处 `finish_reason` 检测
- 修复：显式设 `max_tokens` 拉满到 DeepSeek-V4 输出上限 **384K（384000）**（[官方文档](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)，实测 API 接受），不再用服务端小默认值。
- 兜底：`_call_api()` 检测 API 拒绝该 max_tokens 时自动降级到 32768 重试。
- 截断可见：检测 `finish_reason=="length"` 时在回复末尾追加"⚠️ 已截断，可输入'继续'补全"提示，不再静默。
- 配置：`settings.yaml` 的 `chat.max_tokens`（默认 384000，模型上限 384K）。

> 详见「问题 2」章节。

### 8.3 对抗审查 6 类 bug 修复（2026-07-22，commit 6f661e2）

3 agent 对抗审查发现并修复（详见 git log + `tests/test_chat_history_trim.py`）：
- **H1**：`analyze_stock` 回写 `strategy_state` 到 portfolio.yaml（原只读不写 -> 持仓股 inertia/cooldown/high_since_entry 冻结，chat 与 CLI 随时间分歧）；仅持仓股回写避免为非持仓创建虚假记录。`portfolio.update_from_strategy_decision` 同步修保留 `high_since_entry`（CLI 也受益）。
- **M-H1**：timeout 60->180s（见上）。
- **H2**：`analyze_stock` 的 `get_stock_data` 加 30s daemon 线程超时（复用 CLI 模式，防 akshare 挂起卡死 chat）。
- **M1**：tool_calls 分支检测 `finish_reason=length`（截断时放弃执行残缺 tool_calls + 提示，避免空参执行 AI 装失忆）。
- **M2**：thinking 判断 `startswith("deepseek")` 收窄到 `deepseek-v4`（8 处，回退旧 deepseek-chat 不报错）。
- **M3+低级**：`_call_api` 多级降级 384000->32768->8192->4096 + kimi 用 `max_completion_tokens` + 匹配收窄避免 context 超限误触发 + `_trim_messages` max_history<=0 守卫 + assistant content `or ""` + arguments TypeError 兜底。
- **历史裁剪 fix**（commit 2bb0b0a）：`_trim_messages` 丢弃开头孤立 tool 消息（裁剪切断 assistant(tool_calls)+tool 配对导致 API 400）。
- **rsi_6_series 计算崩溃 fix**（commit 38aac55，2026-07-23）：`akshare_client.calculate_indicators` 算 rsi_6_series 时 `_loss.replace(0, pd.NA)` 变 object dtype，`.round(2)` 对 NAType 崩，导致 calculate_indicators 整个失败 -> 所有技术指标 None -> oversold_confirm 6维全 False 不生效。改用 `float('nan')` + `.astype(float)`。**教训：测试 oversold_confirm 必须跑真实 calculate_indicators，不能 mock StockData**。
