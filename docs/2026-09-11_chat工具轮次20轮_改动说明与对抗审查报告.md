## 三、对抗审查发现

### 🔴 P1-1 轮次翻倍，但单轮对话的上下文预算没有配套护栏

**证据**
- 循环内**只做 append、全程不裁剪**：`src/chat/agent.py:389-509` 的 `while` 体内 5 处 `_messages.append`（428/451/495/528/559），无一处调 `_trim_messages`
- `_trim_messages` 只在**进入循环之前**调用：`src/chat/agent.py:304`（`chat()` 内）与 `:677`（恢复会话）
- 实测体量：`CHAT_SYSTEM_PROMPT` 3,988 字符 + `TOOL_DEFINITIONS`（14 工具）6,634 字符
- 最坏情形单轮请求：3,988 + 6,634 + 20 × 4,000（`max_result_length` 上限）= **≈ 90,600 字符**

**后果（推理链，未联网实测）**：中文约 1 token/字符量级，即逼近 9 万 token 的请求体，显著抬高撞上下文上限的概率（20 轮比 10 轮翻倍）。而 `_call_api` 的降级分支只认 `max_tokens` / `max_completion_tokens` / 中文"输出超过"三种签名（`src/chat/agent.py:172-189`），**上下文超限不在其中 → 直接 raise** → 被 `chat()` 捕获成 `对话处理出错: ...`（`src/chat/agent.py:319`）。用户看到的是通用报错，不知道"是聊太长了"。

**建议（三选一或组合，改动量递增）**
1. 最省：识别 context 超限错误签名，给人话提示（"本轮对话上下文过长，请 reset 后重问"）
2. 中等：对 tool 结果做**累计预算**，超阈值后把最早的工具结果折叠为一行摘要
3. 最重：循环内每 N 轮调用一次 `_trim_messages`——注意会丢早期工具结果（如第 1 轮取到的持仓），需确认可接受

### 🔴 P1-2 工作区存在**未提交**的 model 改名，会让 10 处 V4 分支静默失效

**这不是本次改动引入的**，是 `git diff` 时发现的原工作区状态：

```diff
 configs/settings.yaml
-    model: "deepseek-v4-flash"
+    model: "deepseek-flash"
-    model_pro: "deepseek-v4-flash"
+    model_pro: "deepseek-flash"
```

**静态可确证的影响链**：全库 **10 处**用字符串前缀判断是否 DeepSeek-V4，改名后全部为 False：
```
src/chat/agent.py:159                     src/core/ai_modifier.py:290
src/scanner/scanner_engine.py:773         src/core/event_layer.py:711, 808
src/core/benzong/auto_scorer.py:113       src/core/benzong/theme_locator.py:215, 230
src/data/source_check.py:355              src/core/benzong/dimensions/__init__.py:92
```
对 chat 而言，走 else 分支意味着：① **不传** `thinking.type=disabled`；② 改用 `max_completion_tokens` 而非 `max_tokens`（`src/chat/agent.py:159-168`）。

**待你确认**：这是有意切到新模型别名（那就得同步改 10 处判断），还是误改（应改回 `deepseek-v4-flash`）？我没有联网实测服务端是否接受，不敢替你定论。

### 🟡 P2-1 `max_tool_rounds` 无类型/范围校验，配错即崩（实测）

```
[B] 字符串配置 max_tool_rounds="10" -> hard_tool_round_limit = '1010'
[B] 循环比较抛错: TypeError '<' not supported between instances of 'int' and 'str'
```
YAML 写 `max_tool_rounds: "10"`（带引号）→ `round_num < hard_cap` 直接 TypeError，整个对话崩。**此隐患改动前已存在**（×2 在内部），本次新增的启动横幅会让它更早暴露。另 `max_tool_rounds <= 0` 时循环一次都不走，会直接进入"轮次已达上限"分支，语义怪异。

建议：`chat_cfg.get(...)` 后加 `int()` 转换 + 异常兜底到 `DEFAULT_MAX_TOOL_ROUNDS`，并校验 `>= 1`。

### 🟡 P2-2 20 轮 = 沉默的账单，运行中不显示已用轮次

一轮 = 1 次 LLM 调用；且部分工具内部还会再调 AI（`analyze_stock`、笨总评分每维 1 次）。20 轮上限意味着单次提问可达 **20+ 次 LLM 调用**。当前只在**启动时**报上限，运行中不报进度，用户无法判断"还剩几轮 / 已经花了多少"。

建议：把轮次打进已有的进度行，如 `⏳ 等待 AI 响应...（第 3/20 轮）`——1 行改动，直接满足"用户可感知"。
