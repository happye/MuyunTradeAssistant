# 暮云协作流程（WORKFLOW）

- 生效：2026-10-28。起草：本机 Claude Code 主控，依据用户要求“深入研究 Codex–DSH 协作流程并优化”。
- 地位：**协作流程的唯一规范**。CODEX.md、CLAUDE.md、AGENTS.md、RESUME.md 和各轮计划里与本文件冲突的流程约定，以本文件为准；产品红线仍以 AGENTS.md 为准，计分规则仍以 [PROGRESS_CONTRACT.md](PROGRESS_CONTRACT.md) 为准。
- 依据：[协作优化建议](COLLAB_OPTIMIZATION_PROPOSAL_20261028.md)（问题与证据）、对 codex-dsh 0.1.4 源码与手册的只读研究（结论见第 8 节与 [工具需求清单](CODEX_DSH_TOOL_REQUESTS_20261028.md)）、第十轮 75 个提交的耗时统计。
- 修订：改本文件须在第 12 节留一行记录（日期、改了什么、为什么）。

## 1. 为什么要改（一段话）

第十轮 7 天做了 13 张子卡，台账 10 次记录分数一次没动；`plan/` 新增文本约为产品代码的 7 倍；5 次因额度停止交接，留下未提交 WIP 和永久 STOP_PENDING。根因有四：按“入口”而不是按“能力”切卡；台账大条款永远关不上；每卡自带全套证据和 11 个文档同步；DSH 工具的硬约束（提交即断链、全树指纹、stop 不可逆）被流程放大。本文件逐条给出替代做法。

## 2. 角色

| 角色 | 由谁担任 | 负责 | 不做 |
|---|---|---|---|
| 用户 | 用户 | 方向、V1 范围、费用与授权、需要裁决的问题 | — |
| 主控 | Codex 机器上的 Codex，或本机 Claude Code；由用户指派 | 选卡、写合同、独立验收、Git、台账、文档同步 | 未经用户改派不自己实施产品代码（Codex）；不替用户做范围决定 |
| 实施方 | DSH（Codex 机器）或主控派出的实施子代理（Claude Code 机器） | 按合同改代码与测试、先红后绿、自测 | 提交、改台账、扩范围 |
| 复核方 | 与实施方独立的只读审查（Codex 子代理 / code-quality-guard） | 每卡一次对抗复核，必要时突变探针 | 重复跑未失效的全量 |

**同一时间只有一个主控推进同一张卡。** 换机器、换主控前，先在原机按第 7 节停止模板交接并推送。

## 3. 选卡与卡片

### 3.1 选卡顺序

按下面顺序挑下一张卡，写进 [当前迭代计划](iteration11/PLAN.md) 的队列：

1. 能让台账某条款**真实**从 unknown/unmet 变 met（不是又一次“有限子范围接收”）；
2. 用户跑 `start.py` 能看到差别；
3. 本机离线可完成（公司内网下第三方数据接口与付费 AI 通常不可用）；
4. 依赖已满足；
5. 权重高。

依赖真实外源、真实日历时间、付费 AI 或用户裁决的条款，放进计划的“受限/待决”区，不排在队列前面。

### 3.2 卡号与上限

- 新卡号：`<条款短名>-<序号>`，如 `G5-SOLVER-1`。历史卡号（T04-x、T05-x 等）保持原样，不追改。
- **一个条款最多 1 张主卡 + 1 张追修卡。** 需要第 3 张时停下：写三行复盘（前两张为什么没覆盖、拟拆出的新子条款、预期台账怎么动），经 `scope_change` 拆条款后再开卡。
- 连续两张功能卡台账都不动，第三张开工前先复盘，由主控或用户决定是否继续该方向。

### 3.3 能力–入口矩阵

一个能力要铺到多个命令入口时，开第一张卡前先列矩阵（能力 × 入口 × 差异点），一次盘点完。第一张卡 = 共享件 + 第一个入口；第二张卡 = 其余入口合并。已验收入口不为“统一”而重构，除非有用户可见收益。

### 3.4 合同模板（≤1 页）

```
## <卡号> <标题>（合同 YYYY-MM-DD，主控：<谁>）
- 关联条款与预期台账变化：<条款ID>：工程 x→y / 验收 x→y；或“不动，用户可见价值：<一句>”
- 目标：<用户会看到什么>
- 范围：做 <…>；不做 <…>（含理由）
- 文件所有权：<允许改的文件>；禁止 <…>
- 兼容锁：<必须逐字不变的行为>（对应测试 <file::name>）
- 验收：反例清单 <…>；命令 <守卫 runner 命令>；全量一次（卡终）
- 停止条件：<范围冲突/需改共享件/额度不足 时怎么办>
```

合同提交并推送后再派工（多机器共享）。

## 4. 一张卡的生命周期

| 步骤 | 产物 | 规则 |
|---|---|---|
| 1 选卡 | 计划队列一行 | 第 3.1 节 |
| 2 合同 | DELIVERY 段 ≤1 页，提交推送 | 第 3.4 节模板 |
| 3 实施 | 代码 + 测试，≤3 个切片 | 每切片先红后绿；业务红与缺符号红分列计数 |
| 4 验证 | 定向 + 受影响相关文件 | 第 5 节 |
| 5 复核 | 复核结论（P0/P1/P2） | 每卡一次；P1 必修，P2 酌情 |
| 6 卡终验证 | 最终树全量一次 | 不开 UTF-8 模式；有偶发失败先定位修复，不重跑碰运气 |
| 7 交付 | 代码提交（中文详细说明）+ 推送 | 只 add 本卡文件 |
| 8 同步 | 回执 + 4 个必改文件 | 第 6 节 |

**WIP 上限：每台机器同时只推进 1 张卡。** 发现的卡外缺陷：小于约半小时且同模块的，按“修 bug 四步”单独提交；其余登记 ISSUES，进计划的维护队列。

## 5. 验证

- 统一走守卫 runner：`.venv/Scripts/python.exe plan/fusion/iteration9/review_test_runner.py <测试文件…>`（本机公司内网下普通 pytest 会在外源处挂起）。无参数时只跑其内置清单；全量传 `tests`。
- 分层：切片 = 新测试文件 + 受影响文件；卡终 = 最终树全量一次；改了全局状态、共享 fixture、runner 或共享 helper 时必须全量。
- 全量结果注明：通过/失败/跳过数、耗时、真实退出码、是否 UTF-8 模式、守卫拦截计数。**不加 `-X utf8` 跑全量**（会掩盖测试里不带 encoding 的读写，见 LRN-20261028-CODEPAGE）。
- 并发/超时类测试要给“线程进入被测体”留出数百毫秒调度余量（见 LRN-20261028-FLAKY-TIMEOUT），偶发失败当缺陷修，不重跑碰运气。
- 独立复核方可在临时 git worktree 做突变实验，结束后删除并 prune；不改主工作树。

## 6. 证据、回执与文档同步（单一来源）

### 6.1 回执（每卡一份，目标 ≤5KB）

路径 `plan/fusion/<轮次目录>/<卡号>_ACCEPTANCE.json`，字段固定：

```
schema, date, status, task_ids, base_commit, contract_commit, delivery_commit, related_commits,
roles{implementation, independent_review, controller, model_metadata_verified},
accepted_scope[≤8 条，一句一条],
validation{runner, red_on_base, green_related, full_final_tree, repl_smoke, independent_review, not_verified},
known_followups[], progress{engineering, acceptance, contract_index, closed}, remaining
```

参照：[T05Q_BB_POSPLAN_ACCEPTANCE.json](iteration10/T05Q_BB_POSPLAN_ACCEPTANCE.json)（4KB）。

### 6.2 不再入库

- 逐文件源指纹清单（`*_SOURCE_PINS.json`）：源码身份 = 交付提交 SHA，复核用 `git diff <基线>..<SHA> --stat`。
- 原始测试输出（`*_RESULTS.txt`）：留在运行机本地或 DSH 私有 state-dir，回执写“日志在哪台机器的哪个路径/哪个 runId”。需要长期留证的个别红绿样本，摘关键 ≤20 行进回执。
- 已入库的历史证据不删不迁（台账证据链接依赖它们）。

### 6.3 每卡必改 4 处

1. DELIVERY 卡验收段（≤10 行通俗中文：结论、用户看到什么、怎么验的、没验什么、进度前后、下一步、回执链接）；
2. 回执 JSON；
3. `PROGRESS.json`（证据链接、阻断、下一步、变更记录），随后 `--render` 与 `--check`；
4. `RESUME.md` 当前段（第 6.4 节）。

按触发条件才改：`ISSUES.md`（有问题状态变化，带 file:line、日期、提交短哈希）；`README.md` 版本历史与 `使用手册.md`（只在用户可见行为变化时，写给用户看，不写卡号与测试数字）；`STATUS.md`/`MILESTONES.md`（只在 G/T 状态变化时）；`.learnings/`（有教训时）。

`AGENTS.md`/`CODEX.md`/`CLAUDE.md` 顶部只放**固定的一行指针**（“当前进度与下一步见 RESUME”），不随每张卡改写。

### 6.4 RESUME 当前段（≤8KB，只有一个“当前”段）

```
## 当前：<日期> <主控> <在做/已交付的卡>
- 最近交付：<卡号> <代码SHA>/<文档SHA>；台账是否变化
- 下一步：<一句话，指向计划队列第几项>
- 阻断/待用户决定：<≤3 条>
- 运行中的外部状态：<无 / “DSH 任务在 X 机器，详见该机本地记录”>
- 恢复步骤：读 AGENTS→本段→check_progress --check→按计划队列开卡
- 不要做：<≤3 条>
```

历史段不留在文件里，靠 `git log -p plan/fusion/RESUME.md` 查。

### 6.5 文风

先结论后数字；每个数字说明“是什么”（如“新增 71 项测试全部通过”）；首次出现的缩写给全称；一段一件事，≤约 200 字；精确字段与英文机器字段只放 JSON 回执。

## 7. 额度与中断

1. **开卡前估额度**：剩余额度不够完成一个切片（实现 + 定向验证 + 提交）就不开新切片，只做只读准备。
2. **停在边界**：只在“切片已提交”或“请求已终态”处停。**不用 DSH 的 stop 做额度交接**——stop 不可逆，会话里有过工具调用后就到不了 STOPPED，只会留下永久 STOP_PENDING（见第 8 节）。stop 只用于失控、越界或用户叫停。
3. **不留未提交 WIP**：切片通过即由主控提交推送。切片未完成又必须停：要么放弃并清理工作树；要么把补丁保存在运行机本地（不入库）并在 RESUME 写一行“X 机器 <路径> 有未完成补丁，<卡号> 第 n 切片”。不再出现“禁止重套”的悬空 WIP。
4. **停止交接模板（≤10 行）**，写进 RESUME 当前段：停在哪张卡、哪个切片；最后提交 SHA；未提交内容（无/已放弃/本机补丁路径）；运行中的外部任务（有/无）；下一步第一个动作。
5. **机器运行态不进仓库**：task/session/request id、stopAttempt、cancelAck、本机临时路径，只写在运行机本地（DSH state-dir 或本机笔记）。

## 8. DSH 使用规则（Codex 机器）

研究结论（codex-dsh 0.1.4，代码位置见工具需求清单）：合同绑定执行目录的 HEAD/分支，**一旦提交，该 task 的派发、测试、修订全部失效**；全树指纹覆盖所有被跟踪和未忽略的文件，**改 `plan/` 文档也会让旧回执失效**；stop 只能置位不能撤销；SUBMISSION_UNKNOWN 与未知执行意图会永久阻断该 task；state-dir 与 profile 含本机绝对路径和凭据，**不能跨机器迁移**。据此：

1. **执行目录用专用代码工作树**：`git worktree add --detach <仓库外路径> <main HEAD>`，`nativeCwd` 与 `executionRoot` 都指向它（detached，不建命名分支，符合 CODEX.md 的单人 main 纪律）。主控在主检出目录改 `plan/` 文档和提交，不触碰 DSH 的执行范围。
2. **一卡一个 DSH task**：卡开始时在工作树当前 HEAD 绑定合同；切片验收后，主控把工作树中已验收的改动应用到主检出并提交推送（工作树 HEAD 不变，task 不断链）；卡结束后弃用该 task，工作树重置到新 main，下一卡新 task。
3. **测试用工具自带的 testPlan/run/receipt**：runner=command，executable=`.venv` 的 python.exe，argv=守卫 runner + 测试文件；`runtimeInputs` 列解释器与各发行版 `*.dist-info/RECORD`（环境变化时重生成，清单存运行机本地）。`run`/`receipt` 加 `--output-budget-bytes 16384`，仓库回执只记 runId、回执 sha256 与结论。
4. **观察**：`follow --view summary --request latest --since-cursor N --since-generation H`；一个观察窗口未结束不再开新的 status/follow；不做秒级空轮询。
5. **未知状态当高风险**：额度临界前不启动 send/run；出现 SUBMISSION_UNKNOWN、UNKNOWN 意图时只读核实副作用，不重投、不删锁、不手改账本；该 task 作废，RESUME 写一行，下一卡新 task。
6. **验收不信自报**：DSH 的 COMPLETED 或“通过”只是请求终态；主控读完整答复、实际 diff 与回执后才算接收。

## 9. 多机器与 Claude Code 主控

- Claude Code 机器不使用 DSH（工具合同的 gitOwner 固定为 Codex，state 不可迁移）：由主控 + 子代理（定位、实施、执行、复核、文档）走同一生命周期，回执 `roles` 写实际执行者与模型，型号未核实就写 `model_metadata_verified: false`。
- 不复制 state-dir、不跨机驱动同一 DSH 会话、不重投另一台机器上的未知请求。另一台机器上的 STOP_PENDING 等运行态，只在 RESUME 写一句“仍在 X 机器，原纪律保留”。
- 子代理必须用项目角色（`.claude/agents/`、`.codex/agents/`），工单附文件所有权与三条守卫规则（最小改动、超范围即停、不提交不联网）。

## 10. 度量与复盘

每完成 3 张卡或每周（先到为准）复盘一次，结果写 RESUME 一行，对照下表（基线 = 2026-10-28）：

| 指标 | 基线 | 目标 |
|---|---|---|
| `plan/` 新增行 ÷ `src/`+`start.py` 新增行 | 约 7.2–7.6 | ≤3 |
| RESUME 大小 / `##` 段数 | 55KB / 19 段 | ≤8KB / 1–2 段 |
| 每卡新增证据文件 | 约 200KB | 单份回执 ≤5KB |
| 每卡触及文档数 | 约 11 | 4–5 |
| 台账条款真实移动 | 10 条记录 0 次 | 每张功能卡 ≥1 次或写明用户可见价值 |
| 每条款卡数 | 预算能力 7 张入口卡 | ≤2 |
| 额度停止留下的未提交 WIP / 永久 STOP_PENDING | 1 份 stash / 多个 | 0 |

取数口径：`git log --since=<起点> --numstat --format= -- <路径>` 求新增行；其余看文件与台账变更记录。

## 11. 当前默认与需用户决定的事项

| 事项 | 当前默认 | 需要谁决定 |
|---|---|---|
| 跨机器传递未完成切片 | 不建命名分支；补丁留本机并在 RESUME 登记 | 用户：是否允许 `wip/<卡号>` 分支（需改 CODEX.md 单人 main 纪律） |
| V1-G7-BATCH-BUDGET 剩余深水项（缓存输入资格、硬资源界、物理取消、费用上限） | 暂停开卡，先做价值评估 | 用户：是否纳入 V1，或经 scope_change 拆分/移出 |
| G6 预注册的指标阈值、基线、成本门槛 | 主控起草，不自行冻结 | 用户 |
| RAG 质量验收与 ISS-028“不需人工复核”的冲突 | 维持未满足 | 用户 |
| 边界必要性（G7-BOUNDARY-RESERVE）、写竞态（G7-WRITE-RACE）裁决 | 主控起草裁决包 | 用户或独立审查 |
