# V1任务量化、阶段交付与进度更新合同

版本：`V1-progress-1`，2026-10-25。用户要求把任务、完成结果和剩余工作变为可见账本；本合同由Codex依据现有G/T路线建立，具体状态经过独立文档审查。初始依据是现有合同/历史验收记录，**没有重新逐行审计全部产品代码**，不是投资效果认证，也不是工时估算。

## 1. 一份事实源，三个阅读入口

- [PROGRESS.json](PROGRESS.json)：唯一任务/权重/状态/证据事实源。
- [PROGRESS.md](PROGRESS.md)：自动生成的完整明细，含已闭合、剩余、依赖和解除阻断条件。
- [本地可筛选看板](../../docs/开发进度看板.html)：与Markdown使用同一次计算，按阶段、状态或关键词查看。

[MILESTONES](../../MILESTONES.md)保留目标与结项定义，[STATUS](STATUS.md)保留批次验收，[RESUME](RESUME.md)保留接续信息，[第十轮计划](iteration10/DELIVERY_PLAN.md)保存实施合同；这些入口只引用计分结果，不手写另一份百分比。旧M/F/R批次不是第二套当前TODO。

## 2. 如何计分

每条款有唯一ID、一个计分归属G、验收条件和1/2/3点权重：分别表示小/中/较大交付范围。权重是主控给出的首版管理口径，不宣称是客观工时或用户逐条确认过的投资价值。关联多个T/R只用于检索，不能重复加总。

每条分别记录工程与验收：

| 状态 | 含义 | 如何计分 |
|---|---|---|
| met | 明示范围有已有交付/验收记录支持 | 纳入已确认分 |
| unmet | 明确尚未满足该条标准 | 留在分母，不纳入上下界已完成分 |
| unknown | 当前记录不足以确认，可能已有实现 | 留在分母，仅纳入可能上界；不能说成“未开发” |
| not_applicable | 该工程通道不适用，例如只需真实数据/观察交付 | 按冻结applicability剔除工程分母，须写理由；必需条款验收通道不可用NA绕过 |

工程完成率E = 工程met权重点 / 工程适用总点。

验收完成率A = 验收met权重点 / 验收适用总点。

**V1合同进度指数P = 50% × E + 50% × A。** 当前schema固定50/50，不允许静默调整比例。它回答“这套明示合同已有多少可确认交付”，不是时间完成率、盈利概率或发布许可。

未知上界将unknown权重加入对应已确认分；已知未完成不加入上界。显示“确认下界—可能上界”，上界只表示待核实部分全部成立时的结果，不预测后续开发成功。上下界之间的点需要核证，100减下界也不能直接叫剩余工时。

工程与验收的分母不同，例如真实MID只计验收而不重复发一份“工程实现分”。各G百分比不能简单平均替代整体公式；T标签重叠，更不能相加。G0持续治理不计产品分，本次写账本不会让产品分上涨。

## 3. 什么时候才算完成

条款闭合要求适用工程满足、必需验收满足；整G闭合要求其必需条款全部闭合。V1仍须符合[MILESTONES完成标准](../../MILESTONES.md)：真实中期样板、长期输入资格、组合约束、质量/效果、运维与明确支持范围均按各自门槛验收。

高分不能绕过真实数据、观察期、费用授权或独立审批。批次pytest通过数量、commit数量、写文档数量不计分。修复测试夹具、重跑未变用例不额外加分；发现反例可重开原条款而使分数下降。

历史证据不会因日期旧自动失效；但覆盖被新改动影响或出现反例时，按影响改为unknown/unmet。证据引用保存产品基线提交号，生成链接指向固定Git版本；“定位”是搜索说明，不能冒充真实章节锚点。文件存在只证明引用可达，不证明内容支持该状态。

## 4. 范围、适用性和变更

初始JSON将已有基础与剩余必需交付一起纳入分母。范围指纹包含ID、标题、G/T/R、权重、必需性、验收条件及工程/验收适用性。拆任务时子项权重之和保持不变；不能靠拆卡、删任务、把未完改NA增加百分比。

范围/权重/适用性变化必须追加`scope_change`，登记old/new指纹、old/new总权重、版本与原因，分别说明“实际完成增量”和“范围变化影响”。新缺陷优先重开已有条款；真正新增需求才新增分母。改变50/50则须新计分合同/schema及明确影响说明，不在本版内悄改。

`changes`是显式变更账本，Git保存可审计历史。校验器能发现当前内容与最后范围声明不一致，**不会自动证明baseline没有被整体重写或变更本身合理**；主控须核Git diff并由独立审查检查范围/状态变动。不能把结构校验包装成防篡改安全系统。

历史E3/F1/F2发生在量化基线建立之前，没有冻结的同口径前值，回执保留`progress_delta: null`，不事后编造各批涨了几个百分点。首次草案遗漏/重复边界的修正列在`baseline_audit_notes`，不是一次产品开发增量。

## 5. 下一阶段怎么推进

S1–S5是工作流分组，不要求一个阶段所有历史基础重复验收。已满足的依赖复用有效证据，不重跑未受影响全套。

1. **S1可靠性收敛**：保持已验基础；下一产品合同关联`V1-G7-SESSION`，覆盖登录/心跳/查询/分页/关闭与忙时降级、绝对总截止。
2. **S2真实研究和数据资格**：可与S1并行，推进`V1-G3-REAL-MID`、G4原件/行业时点/ROE/现金资格，不能用mock取代原件。
3. **S3业务闭环**：按依赖核研究视图、成交/组合快照、现金/NAV/数量规则以及批量总预算；T04剩余先做必要性裁决，不自动继续机械拆分。
4. **S4质量和真实观察**：独立集、预注册协议与合法样本先行，真实费用单列授权；观察期未启动时不虚报起止日期或按等待天数计分。
5. **S5发布与移交**：异机、迁移、恢复/退出及全部必需门过关后结项，转维护。

阻断分为code/data/observation/authorization/dependency/decision/verification，每项都有解除条件。依赖未满足不妨碍推进独立的数据取证；不能为消耗额度绕开依赖制造新任务。

历史ISSUES/未做报告中的遗留项集中显示在`legacy_backlog`：映射到当前条款的事项不重复计分；尚未重新核实的候选明确标待复核；用户已否决/接受现状的历史项不复活。待复核不代表从V1免责：若证实影响支持范围，重开相应条款或明确修订范围，G8不能在阻断未清时关闭。

## 6. 每批必须给用户的交付回执

实质开发开始时选稳定任务ID并读取验收条件；新发现先归属再排期。一次有限批次不要求完整关闭一条大任务，阶段性代码和证据也必须说明。

每次交付列出：

- 任务ID、用户可见行为、实际commit与证据入口。
- 本批关闭/重开/仍待核的具体验收条件；未完成原因。
- E、A、P的前值和后值；分母/适用性是否变化。
- 实际完成增量与范围变更影响分别列；维护允许零增量。
- 当前剩余关键项、下一张卡和阻断解除条件。

更新前保存当前`--check`摘要和原JSON引用；更新JSON状态/证据并追加`progress`或`reopen`记录，记录关联任务、前后状态/指标和理由。更新范围另追加`scope_change`。新commit产生前未知的SHA不伪造，可用回执ID在实际Git历史关联；交付后核实main/origin一致。

恢复时先看`--check`摘要与本批任务段，再定向读取相关证据和代码；不每轮全文展开JSON、全部历史账本或数百项hash。全量基线重建/独立审计才需要更广阅读。已有明确授权在适用范围持续有效，先核原授权，不因日期或换会话重复询问，也不凭旧“已授权”标签扩大实验或费用范围。

```powershell
.\.venv\Scripts\python.exe -B -X utf8 scripts/check_progress.py --render
.\.venv\Scripts\python.exe -B -X utf8 scripts/check_progress.py --check
```

正式视图由脚本生成，不手改HTML/Markdown。`--self-test`只验证计算和拒绝边界，不是产品回归。纯进度/文档变更不触发投资产品全量；修改计分器时运行有意义的计算回归和视图检查，产品有改动才按影响执行对应验收。
