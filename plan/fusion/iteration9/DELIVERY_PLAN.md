## P0｜账户异常必须贯穿状态与清单

**映射** R03/R05/R09→G1/G2/G5，T01；**所有权** `src/data/portfolio.py`请求级事实、holding_entries和正式账户回归；必要时只调整既有调用方读取结果，不改事件确认/修复协议。

**方案**：在现有RequestAccountFacts中明确来源完整性和证据优先顺序。账本异常且没有可独立证明的持仓事实时，不能从“查不到lot”或“旧零投影”推导空仓。共享清单在投影枚举异常后传播incomplete，不能只打告警。相同请求的清单与逐股ctx不得互相矛盾，不新建平行账户模型。

**固定验收矩阵**（正常/异常/交叉均须参数化落正式测试；表中数量状态与权重分别断言）：

| 账本/记录状态 | 投影或独立事实 | 预期 |
|---|---|---|
| 正常无账本 | 无投影 | NONE/0、完整空清单 |
| 正常无账本 | 合法旧比例>0 | HELD/原比例，旧正常输出保持 |
| 健康账本、数量0 | 无投影或合法数量0投影 | NONE/0；不报假异常 |
| 健康账本、正数量 | 无投影 | HELD，清单包含该股；缺NAV时权重None、成本不伪造 |
| 健康账本、正数量 | 不一致数量投影 | 保留账本持仓，权重None、对账原因 |
| PARTIAL、有幸存正lot | 有/无投影 | 保留已知持仓方向、权重冻结，清单incomplete |
| PARTIAL、无幸存lot | **无投影与数量0投影分别测** | UNKNOWN/None、不反推股数，清单incomplete |
| 快照读取失败 | **无投影、数量0、正数量投影分别测** | UNKNOWN/None及缺口说明；数量提示不冒充核对通过 |
| 合法YAML但记录解码失败 | 无账本与有独立账本持仓分别测 | 清单incomplete；真la不得说当前无持仓；可独立列出的账本持仓仍保留 |

**必须落地的测试**：先将R15 Z1/Z2转正式红灯，再修；真实文件损坏/条目类型异常不能只用整体mock替代。逐条检查读取前后字节不变；同请求快照次数不增加，下一请求刷新。对相邻旧比例/零比例异常分支列出实际结果及理由，若无法证明独立空仓，不得借正常“无账本兼容”直接放行异常状态。保留硬退出方向与精确新增冻结，不自行恢复丢失成交。

**用户收益/停止/回滚**：损坏或未对账不误报清仓。只用临时1/2/30股样本、零网络/零AI；修复需要回写账户时立即停止该路径并报只读缺口。回滚读侧变更，不撤销任何已确认成交。

## P1｜共享清单和ctx贯穿查仓与启动提示

**映射** R03/R09→G2/G7，T01/T03；**所有权** `src/chat/tools.py:get_portfolio`、`src/cli/main.py:analyze_live`的持仓提示及对应回归。与P0顺序集成，共享文件不交给不同worker并行覆盖。

**方案**：get_portfolio在所有路径读取同一共享清单，不能只有投影空时才补账本；投影细节可保留，但账本独有条目必须列出并标元数据缺口。l/la启动提示按ctx三态显示；pos仅提供可用元数据，不再决定有无仓，不拿旧比例掩盖权重未知。清单不完整须显式提示。

**验收**：

1. 投影独有、账本独有、两边重叠、混合、明确空、损坏/不完整逐项测试；股票代码集合等于已知共享集合且不漏不重复，不只assert“不是空仓”。
2. Z3两条转绿；账本有股时同次l/la输出不得先说FLAT再说有仓。加UNKNOWN提示正例和正常RATIO_ONLY展示兼容。
3. 公共入口的同次上游硬退出→最终包/影子/可见输出一致；只替身行情/外源/触发策略，真实账户装配和最终适配保持真链。数据失败仍不阻断批量后续股。
4. 准确列出today/analyze_industry/TUI/Web的已支持、未支持范围，转录到持久未完成台账（G2/G7/T01），不以文档登记冒充实现。本轮不扩大为多端重写；pos管理命令仍可明确为投影视图。

**用户收益/资源/回滚**：查仓清单完整、同屏不矛盾；无新增网络和写入，旧输出只在错误/缺口场景改变。正常比率账户不强制迁移。回滚只撤展示适配，不删除记录。

## M2｜日常只读研究视图：设计已具体化，生产尚未放行

**映射** R02/R03/R04/R09→G2/G3/G7，T02/T04；**前置** P0/P1独立过门、观察合同冻结。复用[R14已接受原型](../iteration6/m2_readonly_view_prototype.py)；不新做第二套原型。此设计使正常RATIO_ONLY用户也能在l/la看到已接受研究与下一步，不依赖用户先建数量账本。

**产品落点**：在既有`ResearchApplicationService`增加显式只读查询方法（建议`get_daily_view(security_id, as_of=...)`），或同模块小型查询函数；注入plans_store/assessment_store。**不得调用`run(capture=False)`冒充只读**：现有run仍能生成归档、评估和候选。查询无需ResearchStore写通道或fetch_fn，不加新编排层。

**输出合同**：security_id、as_of、store_status（正常/空/损坏或不可读）、MID/LONG各自已接受计划id/revision/精确accepted_ref、被核对的assessment状态与缺口、candidate是否存在/版本、next_steps。已接受槽是主显示，候选未接受不替换；空库给具体research命令，损坏库给核对修复提示，旧方法明确待复核。评估核对复用既有唯一规则，不另发明TTL，不从facts文本重新算VALID。若需要抽共享核对函数，保持shadow及研究消费者回归等价，不让应用服务新增CLI反向依赖。

**入口接线**：l和la共享装配/渲染，只添加简明研究段；正常持仓/退出主结论保持原职责。账本或研究视图失败不吞硬退出。chat/Web/TUI本卡不做研究交互改造，帮助文字如实界定支持入口。详细研究仍由显式research/--capture生成，plan2 accept和风险确认保持显式。

**生产验收清单（前置通过后执行）**：

- 正常接受态、无资料、存在候选、失效/需复核、损坏库、旧方法、MID/LONG并存和重启八类场景；连续l、la、重启读取，研究/计划目录的文件集合及内容哈希不变。
- 记录新增查询网络请求数=0、付费调用=0、研究写入=0；原分析证据/影子正常追加分开计，不把整个l误标零写。
- 返回和用户输出一致；查看时钟变化不产生revision；候选不遮住已接受态，失败不伪装空库。记录附加耗时基线，不凭估计宣传提速。
- 明确启动/异常/回滚路径：只撤只读视图接线，接受态和研究档案保留。无数量账本也可显示研究段；不因此把RATIO_ONLY宣称为完整数量账户。
