- 日期：2026-10-28（证据截止同日）。
- 起草：本机 Claude Code 文档工人，受主控委托；主控审阅并补测了“待确认”数字。读者：Codex（合同/验收/文档/账本/Git 主控）。用户已表示会让 Codex 据此优化协作方式。

## 1. 一句话结论与对四个问题的直接回答

**结论**：需要做的真实工作量，远小于卡的数量。卡多，是四个做法叠加的结果：按入口切卡、逐张衍生、台账条款关不上、每卡都带全套证据。建议改这四处，保留已被证明有效的部分（逐入口真实用法排查、先红后绿、守卫 runner、独立复核）。

1. **是预先规划的，还是做完上一个又衍生的？** 衍生的。每张卡在上一张交付收尾时写「下一卡候选」，再单独落合同。例：T05-L 交付时提出 M；T05-O 的停止交接写「P 仅只读定位」；T05-P 交付时写「下一候选 T05-Q」（读 `plan/fusion/RESUME.md`、`DELIVERY_PLAN.md`）。没有预先的整体拆分表（主控核实）。
2. **真有这么多任务要做吗？** 有缺陷、有缺口，但任务数被切法放大了。可选启动预算加「未开始」口径这一个能力，先后在 `ba`（J）、`l`/`la`/`l all`（L）、`bz scan`（N）、`scan market deep`（O）、`scan`（P）五个入口各做一遍。值得做的是「一个能力加若干入口接线」，不是五张完整的卡。
3. **超过 Z 怎么办？** 现在没有规则。字母编号已经靠二级编号撑着（`DELIVERY_PLAN.md` 里有 E2、E3、F1、F2）。按第十轮前 8 天约 1.6 张/天（13÷8，推算）的速度，Q–Z 约一周用完。根因不是字母不够，而是没有「一个能力最多几张卡」的上限。
4. **有没有做无用功、冗余设计？** 有，也有不冗余的。冗余：同一能力逐入口重做；证据与文档体量（`plan/` 新增行数约为产品代码的 7.6 倍）；台账十条记录分数都不动。不冗余：逐入口过一遍确实挖出过真缺陷（第 2.2 节）。要保留的是「逐入口实际排查」这个动作，不必保留「每入口一整套合同加回执加源指纹加 11 文档同步」这个形式。

### 2.2 现有做法里应保留的部分

1. **逐入口实际过一遍**确实挖出过真缺陷：L 发现「仅行情/未知返回被记成功并写当日已析，`l all` 永久跳过」；N 发现 allrules 忽略 `--limit`；P 发现 `scan 半导体` 静默忽略主题词、对全部持仓跑 AI；P 复核发现汇总表重复行（ISS-135）；正在规划的下一卡发现 `pos plan all --update` 用户答 N 被记为「✗ 失败」、`bb 600519 000001` 把第二只代码当起始日期（主控核实）。
2. 先红后绿、业务红与缺符号红分列：防止测试自己通过自己。
3. 守卫 runner、受保护用户文件前后哈希：多机器、协作工具无文件沙箱（`CODEX.md` 第 20 行）时有实际价值。
4. 独立复核加突变探针（T05-P 的 18 个突变全杀）：对计时、边界类代码有效。
5. 不凭测试数或提交数涨分、层级不混（设计/原型/实现复验/真实效果）：本稿沿用。

要点：这些价值来自「对每个入口跑真实用法」和「先红后绿」，不来自「每个入口一张卡、一套证据、一轮 11 文档同步」。后者可以瘦身，前者保留。
另外，`MILESTONES.md` 第六、七节已经写了「一次只深入少量卡」「不为消耗额度制造新任务」「没有用户收益的顺便优化不加入必做清单」。缺的不是原则，是可检查的触发条件，下面的建议都按「把原则变成可检查规则」来写。

## 3. 优化建议

### a. 卡片粒度：按「能力」切卡，不按「入口」切卡

- **问题与证据**：J/L/N/O/P 五张卡是同一能力换入口，每次重写一套计时和文案（第 2.1 节）。卡逐张衍生、无总表；编号用字母，已出现 E2/E3/F1/F2，没有上限规则。
- **改成什么**：
  1. 开一个能力的第一张卡之前，先写一张「能力-入口矩阵」，放在 `DELIVERY_PLAN.md` 该卡头部。列：能力、入口清单、每个入口的差异点。入口一次盘点完；中途发现新入口只追加一行，不新开卡。
  2. 第一张卡 = 共享件 + 第一个入口。共享件只抽「已在 3 个以上入口逐字重复」的部分（计时截止、「未开始」口径、预算提示/拒绝文案）。解析已有 `_split_budget_option` 和 `batch_scorer.budget_descriptor` 可复用。共享件放哪个位置由 Codex 定，不新增架构层。
  3. 第二张卡 = 「铺开卡」：剩余全部入口合并，卡内按矩阵逐入口列验收行，各入口分开提交（与 f 配合）。
  4. 一个能力最多 1 张主卡 + 1 张追修。需要第 3 张时必须停下，回台账重拆条款（见 b），并写三行复盘：前两张为什么没覆盖；新条款是什么；预期台账怎么动。
  5. 卡号改为「能力代号-序号」（如 `BATCH-BUDGET-1`），不再用字母顺延，也就不存在「超过 Z」。
  6. 每张功能卡头部必须有一行「预期台账变化」或「用户可见价值（用户敲哪条命令会看到什么）」，二选一，不得空。连续两张功能卡台账不动，第三张开工前先做半页复盘，由 Codex 或用户决定是否继续该方向（只触发复盘，不自动禁止）。
- **预期效果**：`bb`、`pos plan all` 合并为一张铺开卡收口，不再逐入口一张；今后同类能力 2 张卡内收口。
- **风险与护栏**：
  - 抽共享件本身可能变成波及已验入口的大改。护栏：抽取卡的验收是「已验入口的既有测试不改断言仍然全绿」，不借机改行为。
  - 合并多入口使单卡体量变大，额度中断损失更大。护栏：卡内按入口分切片提交（见 f）。
  - 矩阵可能漏入口。护栏：追加行规则，漏的入口在已有卡内补，不新开卡。

### b. 台账条款可关闭性：把永远关不上的大条款拆开

- **问题与证据**：`V1-G7-BATCH-BUDGET` 一个条款包着期限、资源、身份、复用、续跑多个互不依赖的维度，权重只有 2。T05-H 至 P 十条记录都是「不变」。子卡只能「限定接收」，台账上永远看不到「这一块完成了」，既无进度信号，也无法判断「做够了」，只能靠开新卡继续。
- **改成什么**：
  1. 经 `scope_change` 登记，把它拆成可独立验收、可独立关闭的子条款（`PROGRESS_CONTRACT.md` 已要求范围/权重变更留版本与前后影响）。下面只是示意草案，具体切法与权重由 Codex 定：
     - 可选启动预算与「未开始」口径：关闭判据 = 入口矩阵每一行都是「已支持」或「明确不支持并写理由」。已覆盖 `ba`/`bz` 多代码、`l`/`la`/`l all`、`bz scan`、`scan market deep`、`scan`；待覆盖 `bb`、`pos plan all`。
     - 任务输入/配置身份：T05-I（ba 执行参数快照）、T05-M（live 批配置冻结）已做的部分归此；关闭判据待定义。
     - 缓存输入资格：T05-K（逐维缓存载荷资格）已做的部分归此；关闭判据待定义。
     - 硬资源界、物理取消、费用上限：目前各卡都写「协作式预算，非强制中断、非费用上限」。这一项要不要做、怎么做（是否需要子进程隔离之类设计变更）见 i，需用户决定。
  2. 每个子条款写「可观察的关闭判据」，不用「核定…全链…」这类无法判定完成的写法。
  3. 子卡交付时，台账变更记录写「本批让子条款 X 的哪一部分满足、还差哪一部分」，不只写「不变」。
- **预期效果**：矩阵项做完时台账能真实移动一次；最难的一项被单独暴露出来，让用户决定值不值得做。
- **风险与护栏**：拆条款可能被看成「凑分」。护栏：拆分前后总权重和适用性不变，拆分当天指数应与拆分前相同，之后只随真实独立验收变化；不用测试数或提交数涨分；已有的 `unknown` 语义保持，不把未知当已做。

### c. 证据瘦身：回执一份、轻量、模板化

- **问题与证据**：Git 提交 SHA 已唯一钉住当时的源码内容，逐文件 sha256 清单（1877 项，含无关文件）重复了 Git 已有的能力；原始测试输出几千行入库；13 份回执共 264KB（平均约 20KB，推算）。本机 T05-P 回执（`plan/fusion/iteration10/T05P_PORTFOLIO_SCAN_BUDGET_ACCEPTANCE.json`，无源指纹）是轻量对照，实测 7480 字节（主控核实），仍高于下文 5KB 目标，说明模板还要再收。
- **合理之处**：「用户本地账户/知识库文件前后没被改」这类证据在无沙箱时有价值，应保留；多余的是 1877 项全量清单。
- **改成什么**：
  1. 不再新增 `*_SOURCE_PINS.json`。源码身份 = 交付提交 SHA + 回执里记「改动文件数、增删行数」（来自 `git diff --stat`）。Codex 验收时用 `git diff <基线>..<SHA> --stat` 对账。
  2. 原始测试输出（`*_RESULTS.txt`）不进 git，放本机忽略目录，回执只记：命令、通过/失败/跳过数、真实退出码、守卫 runner 的三项 IO 计数（网络/子进程/真实状态）、耗时、是否 `-X utf8`、提交 SHA。注意：现在 `.gitignore` 只忽略了 `.cache/harness-agent-routing/`，本机 `git status` 显示 `.cache/` 其余部分是未跟踪，新增忽略条目属配置改动，由 Codex 定。
  3. 回执模板（固定字段，目标 ≤ 约 5KB）：schema/日期/状态；基线、合同、交付提交；接收范围（≤8 条，一句一条）；验证表；红绿证据（红：失败数及类别；绿：通过数）；独立复核（谁、结论、P0/P1 数）；未验证项；进度前后；剩余。T05-P 回执是这个模板的雏形。
  4. 保护文件：只记「受保护文件（≤10 项）前后哈希相等」的布尔结论加这几项哈希，不再列全仓清单。
  5. 存量不动：旧 `SOURCE_PINS`/`RESULTS` 已在 git 历史里，删掉也不缩小 `.git`；是否迁出工作树由 Codex 定（会让 `RESUME.md` 等文档里指向它们的链接失效，需同步改链接）。
- **预期效果**：每卡新增证据文本从粗算约 200KB 降到约 5KB 的一份回执；`plan/` 与代码的行数比明显下降。
- **风险与护栏**：
  - DSH 交付时若还没提交，就没有 SHA 可钉。护栏：验收对象是提交（本地临时提交或 wip，见 f 与第 5 节待决问题），不是工作树文件清单。
  - 日志不入库后，事后复核不到原始输出。护栏：回执写明日志所在机器和路径；需要长期保留的个别红绿样本，摘录关键 20 行进回执，不整份入库。

### d. 交接文档：`RESUME.md` 只留一个「当前」段，机器运行态不进仓库

- **问题与证据**：`RESUME.md` 57KB、19 段、5 段停止交接。前三段含 task/session/request id、sha256、stopAttempt UUID、`C:/Users/Crux/AppData/Local/Temp/...` 本机路径（读文件），对其他工具或机器没有意义，且随机器状态变化立刻过期。`CODEX.md`、`AGENTS.md` 顶部又各复制一份「当前交接」，已出现不一致（第 2.1 节）。
- **改成什么**：
  1. `RESUME.md` 固定结构：只有一个 `## 当前` 段，≤约 8KB。字段固定：谁在做；卡号与基线 SHA；已交付 SHA；下一步一句话；阻断；恢复步骤（≤5 步）；不要做的事（≤3 条）。
  2. 历史段不再留在文件里：首选靠 `git log -p plan/fusion/RESUME.md` 查；若要保留可读历史，合并成一个归档文件、之后不再每次新建（主控核实：`plan/fusion/` 与 `docs/archive/` 下都没有 RESUME 归档；`docs/archive/` 只有几份早期按日期命名的交接文档）。
  3. session/request/stopAttempt/STOP_PENDING/cancel 细节、本机临时路径，只写在运行机本机的忽略文件里。`CODEX.md` 第 20 行已规定所有 DSH 命令复用共享 `--state-dir`，这个目录本身就是运行态账本，身份不必在仓库重复。`RESUME.md` 只写一句「DSH 任务锁在 Codex 机器的 state-dir，换机器时需带上它」。
  4. `CODEX.md`、`AGENTS.md`、`CLAUDE.md` 顶部的「当前交接」改为一行指向 `RESUME.md`，不复制正文。
- **预期效果**：读取成本约降到原来的七分之一以内（57KB→≤8KB）；多个工具读到的当前状态一致。
- **风险与护栏**：换机器恢复时缺 DSH 身份，可能误重投请求（`CODEX.md` 要求「未知提交先 resume，不盲目重发」）。护栏：`RESUME.md` 当前段保留一句「如何找到 state-dir、先 resume 再动作」；历史上已写入 git 的身份信息不追改。

### e. 文档单一来源：交付事实只写一处

- **问题与证据**：每次交付同步约 11 个文档，同一段摘要在 5–6 处重复改写，逐字重复和漂移已有实例（第 2.1 节）。本机 T05-P 这次文档同步的工作树改动同样涉及 11 个文件（AGENTS、ISSUES、MILESTONES、README、看板 HTML、PROGRESS.json、PROGRESS.md、RESUME、STATUS、DELIVERY_PLAN、使用手册；读 git status），所以本条对本机同样适用。
- **改成什么**：
  1. 交付事实（交付提交、范围、证据、限制、进度前后）只写在 `DELIVERY_PLAN.md` 该卡的验收段（≤10 行）和回执 JSON 里。
  2. 其余文件只放一行链接，如「T05-P 已限定接收，见 DELIVERY_PLAN#T05-P」。
  3. 必改清单压到 4 个：`DELIVERY_PLAN.md`（事实）、`PROGRESS.json`（账本，看板/MD 由脚本生成）、`RESUME.md`（一行加下一步）、`ISSUES.md`（状态变更，带 `file:line`、日期、提交短哈希）。
  4. 其余按触发条件才改：用户可见行为变了才改 `README.md`（只写面向用户的版本历史，如「`scan 半导体` 现在会被拒绝并提示」，不写卡号和证据）和使用手册；台账里 G/T 状态变了才改 `STATUS.md`/`MILESTONES.md`。
  5. `PROGRESS.json` 变更记录的说明字段控制在约 300 字，细节用回执链接。实测构成（主控核实）：`tasks` 47 条约 75KB（66%），`changes` 12 条约 16KB（14%），`legacy_backlog` 约 8KB（7%）。`tasks` 偏大的一个直接原因是同一条款的工程证据列表与验收证据列表常常逐字重复（如 `V1-G7-BATCH-BUDGET` 两份列表都是 T05-H…P 共 10 个回执链接），可改为验收侧引用工程侧或只列差异。
- **预期效果**：每次交付触及文档数从约 11 降到 4–5；同一事实只有一个可信位置。
- **风险与护栏**：单个文件不再自足，读者要点链接。护栏：链接用稳定锚点；`check_progress.py` 已校验仓库引用存在（`PROGRESS.md` 第 6 行说明），可复用；不手改生成的 HTML/MD。

### f. 额度/中断策略：卡设计成可中断，不留未提交 WIP

- **问题与证据**：额度不足导致的停止交接有多次（不足 10%/7%/3%）。每次停止都把「在哪、WIP 在哪、锁状态」写成一个长段，且在机器上留下未提交 WIP（本机旧 T05-M WIP 后被远端取代，只能 stash 并禁止重套）。额度是用户的真实约束，不是流程问题；流程问题是「一张卡的进度只存在于未提交的工作树里」。
- **改成什么**：
  1. 每张卡拆成 ≤3 个切片（如：先写红测试 → 共享件 → 入口接线），每个切片自带一条可运行的验收命令。切片通过即由 git_owner 提交。额度不足时只丢当前切片，不丢整卡。
  2. 停止前二选一：提交到约定位置；或明确放弃并清理工作树，在停止模板里写「已放弃，未保存」。不再「留着以后再套」。
  3. 停止交接固定短模板（≤10 行）：停在哪张卡、哪个切片；最后一个已提交 SHA；未提交内容（只能是「无」或「已放弃」）；下一步第一个动作；有无运行中的 DSH 任务（只写有/无并指向本机运行态文件）。
  4. 沿用现有「不重复 cancel、不杀用户共享 Host」纪律，但 stopAttempt 等不再写进仓库。
- **预期效果**：任一机器在停止后几分钟内能按模板恢复；不再出现「禁止重套」的悬空 WIP。
- **风险与护栏（含与现行规则的冲突，需 Codex 定）**：
  - `CODEX.md` 第 40 行写「不自动创建功能分支」「不另建命名分支」，与 wip 分支冲突。两个选项：(A) 在 `main` 做本地提交、验收前不 push，失败则回退；(B) 允许 `wip/<卡号>` 分支，验收后合入并删除，同时修改该句。A 的代价是未验收提交混进主线历史；B 的代价是多一类分支要管理。本稿不替 Codex 选。
  - `CLAUDE.md` 项目硬约束写「每个改动都必须让用户跑 `start.py` 时可感知」。共享件切片本身用户看不到。护栏：用户可感知以整卡交付为准，切片是过程提交，提交说明标「内部切片」；这条是否放宽需用户确认。
  - 切片只含通过本切片测试的代码；入口接线未完成的切片不暴露给用户命令。

### g. 文风：固定模板，通俗中文，先结论后数字

- **问题与证据**：交接和卡片高度压缩、缩写密集，如「12+2业务红留证，此前714相关加最终受影响114通过（pytest1.26s、wall3.083s、真实exit0/守卫IO0）增量接收」。缩写和数字链没有定义，人和其他 Agent 都要靠猜或回头对照回执才能确认含义。
- **改成什么**：
  1. 交付摘要固定模板（≤8 行）：结论一句（通过/限定通过/未通过，及范围）→ 用户能看到什么变化 → 怎么验的（命令、通过数、失败数）→ 没验什么 → 进度前后 → 下一步。
  2. 先结论后数字，每个数字带「是什么」，如「新增 71 项测试全部通过」，不写不带解释的「714+114」。
  3. 禁止无定义缩写串：首次出现给全称或链接；常用词放一个术语小表（本稿第 0 节是样例）。
  4. 一段一件事，≤约 200 字；更长的细节放回执。
  5. 英文机器字段只放 JSON 回执；Markdown 用通俗中文。
- **示意改写**（含义以原回执为准，数字不在此重新解释）：原句可写成「T05-O 限定通过：新增测试先在旧代码上因业务行为不符而失败并留有证据，修复后转绿；最终受影响的 114 项测试通过（守卫 runner，耗时约 3 秒，退出码 0，网络/子进程/真实状态访问均为 0）；此前相关的 714 项也通过；未做最终树的一次性全量。」
- **预期效果**：新接手者读一张卡 ≤2 分钟能说清「做了什么、验了什么、还差什么」。
- **风险与护栏**：改写可能丢精度。护栏：精确数字和原始字段保留在回执里，Markdown 摘要只放结论级数字，并链接回执。

### h. 验证：保持守卫，分层跑，放宽单一执行方瓶颈

- **问题与证据**：公司内网下普通 pytest 会在真实外源挂起，守卫 runner 是必需的。`-X utf8` 掩盖了测试里不带 encoding 的读写，本次全量因此有 1 个失败（`d760708` 修复）。DSH 是唯一测试执行方，它忙、受额度限制或被 STOP_PENDING 锁住时，验收可能要等。历史上有全量多次重跑（如 T05-M 第一次全量退出码为空，第二次才取得真实退出码 0，见 `RESUME.md`）。
- **改成什么**：
  1. 守卫 runner 不放宽，业务红/缺符号红分列照旧。
  2. 分层：卡内 = 新测试文件 + 受影响的相关文件；全量只在改了全局状态、fixture、runner、共享 helper 时，或整卡终验时跑一次。回执注明是否 `-X utf8`。
  3. 测试里文本读写显式写 `encoding="utf-8"`。本机 T05-P 做过一次隐式编码读写的 AST 扫描（回执 `same_class_scan`：产品代码 0 处、测试 1 处已修）。建议把它做成一个常驻测试（一次写好，之后每次全量自动覆盖），而不是每卡人工扫一遍；这需要另立一张很小的卡，由 Codex 决定。
  4. 瓶颈放宽：DSH 作为唯一测试执行方被阻塞时，允许主控或独立复核方在同一守卫 runner 下复跑「定向集」（新文件 + 受影响文件），结果与 DSH 结果并列写入回执并标明执行者；全量仍由约定的单一执行者跑，除非用户另行指定。参照：T05-P 的测试由本机实施方（muyun-coder）执行，复核方（code-quality-guard）另在临时 worktree 里用守卫 runner 跑探针和突变，并非单一执行方（回执 `contract.roles`）；这只是一次单机样本，不证明该做法在 Codex–DSH 间可行。
- **预期效果**：全量次数下降；编码类缺陷在卡内被发现，而不是留到全量才暴露。
- **风险与护栏**：多方执行可能结果不一致。护栏：回执写明解释器、runner 路径、是否 `-X utf8`；不一致时以 runner 输出为准并升级核查，不取平均；不得用未失效的旧全量冒充新树结论。

### i. 价值排序：先评估再排期，避免继续按入口铺开

- **问题与证据**：`V1-G7-BATCH-BUDGET` 权重 2/111，已在 T05-H 至 P 投入 10 次台账记录，分数未动。它剩下的「深水项」是缓存输入资格、硬资源界、物理取消、费用上限。T05-O、T05-P 等卡都写明现在是协作式预算、非强制中断、非费用上限，要做到硬界很可能是设计变更（例如进程隔离），不是再接一个入口。同时，`plan/fusion/PROGRESS.md` 的验收下界显示 G5 13.3%、G6 33.3%、G4 26.3%，T06 17.6%、T07 13.0%、G8 0%，而 T05 为 61.5%、G7 为 42.4%。
- **改成什么**：
  1. 对 BATCH-BUDGET 剩余项做一页「价值评估」，不写代码。每项写：用户痛点（有没有真实用户反馈或事故）、预期台账变化、估计成本（卡数、额度）、能否仅靠产品代码实现。评估后三选一：做 / 并入别的卡 / 提请用户决定是否移出 V1 范围（`MILESTONES.md` 第七节要求移出须有明确范围决策，不能默默放弃）。
  2. 评估完成前，不再新开「再一个入口」的预算卡。`bb`、`pos plan all` 合并成一张铺开卡（见 a）。本机已按此执行：T05-Q 合同（`f53f1d3`）把两个入口合并为一卡，并把 `pos plan all --update` 误记失败、`bb` 参数误读作为卡内缺陷行；合同末尾写明“本卡后不再按入口追加字母卡，剩余深水项先评估用户价值”。ISS-135 已在 `5870ae8` 单独修复（四步，带回归测试）；ISS-131 仍待排。
  3. 方向候选（点到为止，不是决定）：
     - G6 的真实前瞻观察需要日历时间，越早起算越好（`MILESTONES.md` 第四节第 4 点「真实时间可与工程工作并行」）。
     - G5、G4、T06、T07 的验收分明显低于 T05。
     - 是否转向、转向哪里，由 Codex 与用户定。
- **预期效果**：额度流向用户可感知、台账分数能动的方向；BATCH-BUDGET 的剩余项有明确去留。
- **风险与护栏**：BATCH-BUDGET 长期不闭合会让 G7、V1 保持未闭合（`MILESTONES.md` 第七节）。这是事实，不是风险被隐藏：护栏是把去留决定摆在台面上，由用户拍板，不用「卡越来越多」来回避决定。
